An orders table in a production PostgreSQL database (about 2,000 writes per second at peak) must be replicated to the lakehouse with under 5 minutes of lag. Rows are updated in place and sometimes hard-deleted, and analysts need deletes reflected too. The DBA insists on minimal extra load on the primary.

Which approach meets these requirements best?

  2. BRead the database's write-ahead log with a tool such as Debezium, publish the changes to a stream, and apply them to the lake table with a periodic MERGELog-based CDC reads changes the database already writes to its log: inserts, updates and deletes, in commit order, with little overhead on the primary and seconds of lag.correct answer

logins(user_id, login_date) has at most one row per user and day. You want each user's streaks of consecutive login days (start, end, length).

Which expression, computed in a subquery and then used as a grouping key together with user_id, puts each streak in its own group? (PostgreSQL syntax: date - integer gives a date.)

  1. Alogin_date - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date)::intWithin a streak, the date and the row number both increase by 1 per row, so their difference is constant; any gap changes it. Grouping by it gives one group per streak.correct answer
  2. Blogin_date - LAG(login_date) OVER (PARTITION BY user_id ORDER BY login_date), the number of days since the previous loginThis is 1 inside a streak and larger after a gap: it marks where streaks break, but all the days of all the streaks share the value 1, so grouping by it merges the streaks.
  3. CDENSE_RANK() OVER (PARTITION BY user_id ORDER BY login_date)With one row per day, this is just a row number: every day gets its own value, so each group is a single day.
  4. DEXTRACT(WEEK FROM login_date)Calendar weeks split streaks that cross a week boundary and merge separate streaks within the same week.

This is the classic gaps-and-islands technique. Number each user's rows in date order: inside a run of consecutive dates, the date and the row number increase in lockstep, so date − row_number is the same for the whole run and changes after any gap. Then GROUP BY user_id, grp with MIN(login_date), MAX(login_date) and COUNT(*) gives the streaks. The LAG approach also works, but needs a second step: flag the rows where the gap is greater than 1, then take a running sum of the flags to number the streaks.
